# v0.1.6 嗅探能力增强开源调研报告

日期：2026-10-04（Asia/Shanghai）。基线：v0.1.5 已失败关闭（资产保留于 `feat/v0.1.5` 并合并至 `main@2b5cbbb`），本文为 **v0.1.6 规划输入**（在 `feat/v0.1.6` 上定稿）。

性质声明：本文是**探索性调研报告**，不改动任何产品代码。文中对 PureBrowser 现状的描述基于 v0.1.5 收尾源码快照（`feat/v0.1.5` 合并点）。文中两个实测失败站点以「站点A／站点B」代称。

---

## 1. 背景与调研目标

实测反馈：在站点A、站点B 的视频详情页，当前嗅探无法命中正文视频（资源面板中只有广告/图片类干扰项，或干脆没有可下载候选）。用户此前的参照产品（通用嗅探类浏览器/扩展）在同一页面能：

1. 嗅探出**正确的正文视频**（而非预览图、广告短片）；
2. 直接给出**多分辨率可选列表**并逐档下载。

参照产品并未对站点逐一下发规则，因此本报告的核心问题是：**业界通用的"高级发现/嗅探"由哪些可复制的通用技术构成？PureBrowser 缺哪几层？**

调研于 2026-10-04 完成，证据共三源：两轮开源项目检索（15+ 个，源码全部本地化阅读取证，见附录 A）、yt-dlp 提取器源码（§7）、以及一款同类商业产品的本地架构分析（§5.9；完整材料仅存本地研究目录，不入库）。

## 2. 调研方法与范围

- GitHub 检索 + topic 页（`m3u8`、`video-sniffer` 等）+ 中文社区线索；
- 对重点项目整仓下载源码（codeload tarball，本地 `/tmp/ghresearch/`），直接阅读检测/解析核心代码，不依赖 README 自述；
- 以 yt-dlp 对站点A、站点B 的提取器源码作为"页面里到底有什么"的权威证据；
- 对 Google Play 一款同类商业产品（视频下载器，内置浏览器嗅探）做本地架构分析，验证分层模型在真实商业实现中的形态（结论见 §5.9；分析材料仅存本地，不入库）；
- 对 PureBrowser 当前实现做同口径管线梳理，用于差距映射。

入选标准：通用媒体嗅探（非逐站脚本集合）、检测逻辑开源可读、优先选取与 PureBrowser 同平台（Android/WebView）或同产品形态（内嵌浏览器+嗅探+下载）的项目。

## 3. PureBrowser 当前嗅探架构基线（源码快照）

### 3.1 管线

```
页面导航（epoch 重置）
  ├─ A. WebViewClient.shouldInterceptRequest   app/src/main/java/com/example/purebrowser/browser/BrowserEngine.kt:100
  │      仅 GET；只读 URL + Range 请求头 → Evidence.REQUEST；返回 null（不构造/不读 WebResourceResponse）
  ├─ B. WebView.setDownloadListener            BrowserEngine.kt:124 → Evidence.DOWNLOAD（含 mime/长度）
  └─ C. 每 2s 注入只读 MEDIA_SCAN              BrowserEngine.kt:181,238
         • <video>/<source> 的 currentSrc/src、播放态 → Evidence.DOM
         • JSON-LD VideoObject.contentUrl      → Evidence.METADATA
         • performance resource timing（近 200 条）→ Evidence.TIMING
         • 同源 iframe 遍历（深度≤2，≤8 帧；跨域早退）
                ↓
  分类（仅 URL/已知 mime，无网络）：media/MediaCandidate.kt:31-79
         m3u8/mpegurl→HLS；mpd/dash+xml→DASH（仅标记）；mp4 等扩展/video/*→FILE；
         ts/m4s/aac/vtt 及 init/seg*.mp4→丢弃；blob:+videoElement→LOCAL；弱端点启发→UNKNOWN（限 32 条）
                ↓
  合并/去重/排序：media/ResourceSniffer.kt:7-75（URL 去片段为键；playing+DOM > DOM > DOWNLOAD > 其他）
                ↓
  UI：ui/resources/ResourceCenter.kt（可下载直链 + 其他媒体两组）
                ↓
  解析（全部用户点击触发，从不自动）：
         • HLS：download/hls/HlsResolver + HlsPlaylistParser（master 变体、#EXT-X-STREAM-INF、默认≤1080p 档）→ TS 下载 → TsToMp4Remuxer
         • UNKNOWN：media/resolver/MediaProbe（匿名 64KiB Range 前缀探测 #EXTM3U / ftyp）
         • 站点适配器：media/resolver/SiteResolverRegistry（YouTube、PeerTube 两个，定位为"协议适配器"）
```

### 3.2 设计红线（v0.1.5 既定，见 docs/EXECUTION-PLAN-V0.1.5.md）

- 不代理、不读取 WebView 响应体；`shouldInterceptRequest` 纯被动；
- 不 hook 页面 fetch/XHR/MediaSource（文档仅列为"可能的未来受限选项"：EXECUTION-PLAN:103）;
- 主动探测必须用户触发、有固定预算（64KiB/2MiB/20 请求）、默认匿名（HLS 可选同源 Cookie）;
- 不做 DRM/付费墙/验证码绕过；不承诺通用动态 DASH/MSE 全覆盖（EXECUTION-PLAN:79-81）。

### 3.3 文档已记录的已知缺口

- DASH 只有标记没有下载（ResourcePresentation.kt:22-23）；
- HLS 子集很窄：仅未加密 VOD、TS 分片、H.264+AAC、拒绝独立音轨/字幕轨（TED 案例因此全军覆没，见 V0.1.5-ROUND-TWO.md）；
- YouTube 完整传输 403 未解；跨站增益门槛未达；
- blob:/MSE、跨域 iframe、Service Worker 流量为已声明盲区。

### 4.2 值得注意的横向事实

1. **所有成功产品都是"分层叠加"，没有单点魔法**：网络层观察 + 页面脚本钩子 + 页内数据扫描 + 主动验证，至少占两层。
2. **"通用为主 + 少量高价值站专用通道"是行业共识**：mediago、flowpick 均内置 B 站/抖音/小红书等页面级派发规则，但不以此替代通用层。
3. **规则外置化是另一种架构路线**（legado/miru/TVBox 家族）：站点适配是可更新的数据，App 本体保持通用。

## 5. 重点项目深度分析

### 5.1 mediago —— 最完整的产品级参照

源码：本地 `/tmp/ghresearch/mediago/`（monorepo：`packages/mediago-extension`、`packages/common`、`apps/electron`）。

**双面规则表（一份数据，两处共享）**：`packages/common/src/sniff/filter-rules.ts` 定义 `SNIFF_FILTERS`：

- 通用规则：`matches: [/\.m3u8/]`、`matches: [/\.(mp4|flv|mov|avi|mkv|wmv|m4a|ogg...)(?![a-zA-Z)/]` 按**请求 URL 的 pathname** 匹配；
- 页面规则：`hosts: [/^https?:\/\/(www\.)?bilibili.com\/video/]` 等按**整页 URL** 匹配后派发到专用提取通道（bilibili、yt-dlp 通道、小红书……）；
- 该表同时被 Electron 嗅探服务与浏览器扩展后台引用，保证两套表面行为一致。

**检测时机**：扩展端刻意选 `webRequest.onSendHeaders`（sniffer.ts 注释：与 Electron 端嗅探相位保持一致），并在此阶段**捕获完整请求头**——`formatHeaders()` 把请求头转成 `Name:Value\n` 格式随源传递，**下载表单直接复用页面当时的请求头**（Cookie/Referer 原样透传，这是对 CDN 鉴权 403 的通用解法）。

**检出即自动解析（inspection 队列）**：检出候选后并不立即上 UI，而是进入 `pendingInspections`，150ms 去抖后批量调用 `inspectSources()` 拉取 m3u8 并解析出 `HLSMediaInfo`（变体/分辨率/码率），**用户看到的列表天生带清晰度档位**。每个 tab 维护 `tabGenerations` 代际号，翻页后旧代际的 inspection 结果直接丢弃——与 PureBrowser 的 epoch 概念同构。

**Electron 侧**（`apps/electron/src/services/sniffing-helper.service.ts`，686 行）：`session.webRequest` 同时挂 `onSendHeaders` 与 `onHeadersReceived`，后者用 `isHLSContentType()`（四个 HLS Content-Type 白名单）做**响应头确认**；支持 `useSessionCookies`；另有 "agent" 模式：无头开页、静默期判定、超时收集的自动化采集器。

**对 PureBrowser 的直接启示**：检出→去抖→批量解析→带会话→代际防串页，整条流水线都可以在 v0.1.6 里用"用户点击触发的解析"升级为"限额自动解析"来对标。

### 5.2 cat-catch 猫抓 —— 检测面最全的扩展

源码：本地 `/tmp/ghresearch/cat-catch-master/`。

- **网络双事件**：`js/background.js:64` 挂 `onSendHeaders`（保存请求头 + 正则匹配 URL），`:76` 挂 `onResponseStarted`（响应头到手后再判一次，"保证有更多信息判断资源类型"）；失败的由 `onErrorOccurred` 清理。用户可自配正则白/黑名单（`G.Regex`），黑名单命中会把 requestId 拉黑跳过 onResponseStarted 阶段。
- **页面注入全家桶**（`catch-script/`）：
  - `catch.js`（937 行）：**代理 `MediaSource` 方法**（MSE 捕获）；去 iframe `sandbox` 属性（绕过受限播放器容器）；Trusted Types 处理；悬浮 UI；
  - `search.js`（867 行）：**深扫页面文本**（含 base64/hex 内嵌数据、`URI="..."` 属性），并**包装 `Worker` 构造器**把嗅探脚本注入页面的 Worker 上下文（很多播放器把清单请求放在 Worker 里）；
  - `recorder.js`：**MediaRecorder 录制兜底**（可选码率/帧率/ffmpeg 转码），用于完全拆不出 URL 的 MSE 页面。
- **下载侧**：内置 hls.js/mux.js/mpd-parser（m3u8.html / mpd.html / downloader.html），AES-128 解密、TS 合并 MP4。

**对 PureBrowser 的直接启示**：`search.js` 的"页内文本深扫 + Worker 注入"是 L3 层的完全体；recorder 是 L5 兜底的现成参考。

### 5.3 Cachelio / VBrowser-Android —— 同平台（Android WebView）的两代实现

VBrowser-Android（2017，Java）→ Cachelio（2024+，Kotlin/Compose），类名同源（`VideoSniffer`/`VideoFormatUtil`），是同一套模式的两代实现：

**宽口径拦截 → 队列 → 多线程自动探测验证**：

```
shouldInterceptRequest（GET + isSniffCandidate 宽过滤）
   → LinkedBlockingQueue/Channel 队列
   → 5 个工作线程消费，每个候选：
       ① 取 CookieManager 的该 URL Cookie + 页面 URL 作 Referer
       ② HttpClient.probe 拿 Content-Type / Content-Length / 重定向后真实 URL
       ③ VideoFormatUtil.detectVideoFormat(url, contentType) 判格式（扩展名优先，mime 兜底，
          octet-stream 仅在 URL 有媒体暗示时接受）
       ④ m3u8 再拉正文验证 #EXTM3U 并累加 #EXTINF 求时长（master 则递归一层）
       ⑤ 失败可重试（retryCount），成功后进 foundList / 发 newItem 事件
```

（VBrowser：`app/.../VideoSniffer.java` + `util/VideoFormatUtil.java`；Cachelio：`data/sniff/VideoSniffer.kt` + `data/sniff/VideoFormatUtil.kt`，后者为协程化版本。）

**页面端注入**（Cachelio `BrowserScreen.kt` 的 `SNIFF_HOOK_JS` + `SCAN_MEDIA_ELEMENTS_JS`，约 40+60 行）：

- `addJavascriptInterface(SniffJsBridge)` 提供 `onMediaUrl/onMediaUrls` 桥；
- hook `XMLHttpRequest.prototype.open` 与 `window.fetch`：URL 命中关键词（`.m3u8/.mp4/.flv/.webm/.mkv/playlist//hls//manifest/playurl`）即上报——**只读 URL，不改行为**；
- 定期扫 `<video>/<source>/<audio>` 的 currentSrc/src 连同就近标题（og:title/figcaption/heading）上报。

**本地代理模式（VBrowser 独有）**：内置 NanoHTTPD（`WebServerManager` + `fi.iki.elonen.InternalRewrite`）——本地起 HTTP 服务改写/中转请求（补头、去防盗链），播放与下载统一走 `127.0.0.1`。Cachelio 亦有 `data/hls/LocalHlsServer.kt` 同思路。

**对 PureBrowser 的直接启示**：这证明在**不触碰 WebView 响应体**的前提下，"自动验证 + 页面会话"可以完全由自有 HTTP 客户端完成——与 v0.1.5 红线兼容的 L1/L4 实现路径。

### 5.4 live-stream-downloader —— Blob 代理与响应头记录

源码：本地 `/tmp/ghresearch/lsd/`（v2/v3 双版本）。

- **Blob 构造器代理**（`v3/plugins/blob-detector/inject/main.js`，约 20 行核心）：页面脚本注入后用 `Proxy` 包住 `self.Blob` 构造器，凡以 `type: 'application/vnd.apple.mpegurl'` 构造的 Blob（播放器在内存里拼 m3u8 的标志）就把完整内容经 DOM 事件抄走。**专治"清单从未上网络"的场景**——这是所有网络层方案的天生盲区，也是被普遍忽视的一招。
- **响应头记录**（`v3/network/core.js`）：固定记录 `content-length / content-range / accept-ranges / content-type / content-disposition` 五个头，用于可下载性与断点续传判断；扩展类型三级可配（core 视频+音频+流 / extra 压缩包 / sub 字幕）；远端 JSON 维护禁止下载的 host/流黑名单（防把播放器自身 CDN 的小文件当视频）。
- v2 附带原生 m3u8-parser 与分段下载管理。

### 5.5 hls-downloader / The Stream Detector / flowpick —— 三种检测取向

- **hls-downloader**（`src/background/src/listeners/addPlaylistListener.ts`）：`webRequest.onCompleted` + 请求类型仅 `xmlhttprequest` + URL 模式 `*://*/*.m3u8*` + **响应头 Content-Type 必须是两个 HLS mime 之一**——四重条件把误报压到极低；检出后由 m3u8-parser 解析 master，前端呈现"选视频流/音频流"。下载侧含 AES 解密（crypto-decryptor）、ffmpeg 合成（ffmpeg-muxer）、OPFS/IndexedDB 磁盘化存储。
- **The Stream Detector**（`src/js/components/supported.js`，67 行）：**扩展名 + Content-Type 的成对规则表**，覆盖 HLS/DASH/HDS/MSS 四种流 + 五种字幕 + 十种文件格式（m3u8/mpd/f4m/ism/vtt/srt/ttml/dfxp/mp4/m4s/ts/aac/mp3/ogg/webm…）。这张表可直接作为 PureBrowser 分类规则的对照基线。
- **flowpick**（`entrypoints/injected.ts` 1286 行 + `background.ts` 2841 行）：main-world 注入，hook `fetch`/`XMLHttpRequest`（只读 URL）+ **MSE 完整捕获**（代理 `MediaSource.prototype.addSourceBuffer` 与 `sourceBuffer.appendBuffer`，把每路流缓存在内存，事后用新 MediaSource 重放校验可播性）+ 页面状态对象读取（B 站 `__playinfo__`/`__INITIAL_STATE__`，含 SPA 导航后的陈旧状态防御）；后台 `onBeforeRequest` 观察 media/xhr/other。同时**明确排除 YouTube**、内置 B 站/抖音页面级适配——再次印证"通用打底+高价值站专用"共识。

### 5.6 下载引擎与解析库

- **N_m3u8DL-RE / N_m3u8DL-CLI**：M3U8/MPD/ISM 统一下载器。能力清单：多线程分片、AES-128/ SAMPLE-AES 解密、live 录制、自定义请求头（`--header`）、自动合并（mp4box/ffmpeg）、多码率选择（`--select-video`）。v0.1.6 若重写下载数据面，此为功能对照表。
- **globocom/m3u8**（Python）：`M3U8/Playlist/Segment/Media/Variant` 对象模型，master/media 两态、IV/KEY、byterange、alternative renditions 全建模——比 PureBrowser 现有 `HlsPlaylistParser` 覆盖面宽，可作为扩展时的模型参考。
- **Momo707577045/m3u8-downloader**：纯前端 fetch+解密+合并的实现样本（AES-128 WebCrypto 路径）。

### 5.7 规则引擎家族（legado / miru-app / TVBox 系）

共同架构：**App 本体只提供运行时（WebView + JS 引擎 + 规则解释器），站点适配是外置的 JS/JSON 规则，由社区维护、可热更新**。

- legado（Kotlin）：书源/订阅源规则（JSON+JS），`JsExtensions` 提供受控宿主 API；需动态渲染的页面用内嵌 WebView 分析。
- miru-app（Flutter）：`flutter_inappwebview` + JS 扩展运行时（`lib/data/services/extension_service.dart`），视频/漫画/小说统一扩展模型。

对 PureBrowser 的意义：与"协议适配器而非站点清单"理念可衔接——**适配器接口不变，实现从内置代码演进为可外置规则数据**，可覆盖长尾站点而不膨胀 APK。属远期支线，非 v0.1.6 必做。

### 5.8 androidx.media3 官方离线能力

`androidx.media3.exoplayer.offline.DownloadManager` + `HlsDownloader`/`DashDownloader`/`ProgressiveDownloader`（+ `CacheDataSource`）：manifest 解析、分片调度、断点、失败重试、合并全为官方实现。注意点：其输出是**离线缓存格式**（供 ExoPlayer 离线播放），导出通用 mp4 成品仍需 remux——PureBrowser 已有 `TsToMp4Remuxer`，因此更现实的用法是**只复用其解析器**（`DashManifestParser`、HLS playlist parser）先解决"看懂 DASH、列出 Representation 档位"，下载数据面再决定自研或借力。

### 5.9 商业同类产品分析验证（Video Downloader 类应用）

第三条证据线：对 Google Play 一款商业"视频下载器"（内置浏览器 + 实时嗅探 + 下载，2025-12 构建，广告变现）的本地静态分析。**本节只摘录与 v0.1.6 相关的架构结论**；完整分析材料（报告、技术清单与规则模式目录）仅存本地 `docs/research/video-sniffer-re/`，不入库，正式文档不展开其获取方式（§10-D4）。

其嗅探由五层组成，与本报告 §6 模型逐层对应：

| 竞品层 | 机制 | 对应模型 | PureBrowser 现状 |
|---|---|---|---|
| 1 | WebView `shouldInterceptRequest` 扩展名/类型通用嗅探；建档时自动附 CookieManager Cookie + 请求 UA/Referer | L1 | 已有观察，无会话附带 |
| 2 | 主动探测：`Range: bytes=0-1` 拿精确大小与断点支持；无扩展名 URL 直接 GET 看 Content-Type 分流 HLS/DASH | L1/L4 | 有 64KiB 探测（更重），无 Range 探测 |
| 3 | `ServiceWorkerClient.shouldInterceptRequest`（API 24+）拦截 SW 分发的 m3u8，并规避 Android 11 已知问题 | L1（开源调研未覆盖） | 已声明盲区 |
| 4 | 页面 JS 注入 + 33 个方法的 JS 桥（`GetPear`），含 `m3u8Content(...)`——**清单由注入 JS 在页面上下文 fetch 后直接回传内容** | L2/L4 | 无注入 |
| 5 | 加密资产内置站点规则（YouTube 正则、X 的 GraphQL 端点模板等）+ 按站截获凭据请求头（Instagram `X-IG-App-ID/X-CSRFToken` 三件套、X 的 `authorization/guest-token`、FC2 API token） | L3/支线 | 无 |

对本报告最有增量价值的四点：

1. **Service Worker 拦截是开源调研的漏网之层**。全部开源扩展方案的 webRequest 天然覆盖 SW 流量，因此没有项目专门处理；而 Android WebView 上 SW 分发的清单是真实存在的盲区（PureBrowser 文档已声明）。竞品用 `ServiceWorkerController.setServiceWorkerClient()` 补上并实证有效——v0.1.6 应纳入。
2. **"页面上下文取回清单"（`GetPear.m3u8Content` 模式）**：m3u8 由注入 JS 用页面自身的会话（Cookie/登录态/防盗链全部天然正确）fetch 后经 JS 桥回传内容，App 端无需自己拼会话。这是 §9 Step 3（请求头透传）的替代/补充方案，对站点A 的年龄 Cookie 场景尤其对症。
3. **播放器指纹是 tube 站长尾的通用钥匙**。注入脚本按 `flashvars`/`kvsplayer`（KVS＝Kernel Video Sharing，海量小 tube 站的通用建站方案）/`html5player`/`xplayerSettings`/`stream_data` 等播放器家族指纹识别并提取源——**按播放器家族而非单站覆盖长尾**。这与 §7 的 yt-dlp 证据完全互证：站点A 的 `flashvars`、站点B 的 `html5player` 正是这类播放器家族成员。
4. **该产品对站点A/B 及同系成人 tube 站同时准备了专用正则与 DOM 特征注入**（如 `div[data-video-id]`、推荐区自动滚动提高发现率），即"通用层优先命中、站点清单兜底"在真实商业实现中成立。其站点规则以内置资产形式打包；按 §10-D4 决策，其中的通用规则模式（扩展名分类、播放器指纹、探测/记录模式等）可直接采纳为 v0.1.6 设计输入。

其他可借鉴细节：`Range: bytes=0-1` 的极小成本探测（两个字节即得精确大小与断点支持，比现有 64KiB 前缀探测轻两个数量级）；下载链路为 FileDownloader + libmobileffmpeg 合并转封装；其规则资产以内置加密形式分发的事实，说明"规则即数据"确为该品类核心竞争力，与 legado/miru 生态化路线互证。

## 6. 通用技术分层模型（调研结论的综合）

```
L1 网络层观察
   URL 模式/扩展名匹配（pathname 级，如 /\.m3u8/、/\.(mp4|flv|mkv)(?![a-z])/）
   + 响应头确认（Content-Type ∈ HLS/DASH 白名单；content-length/range/accept-ranges）
   └ Android WebView 拿不到响应头 → 两条替代路：
      a) 自有 HTTP 客户端"带页面会话的自动探测"（VBrowser/Cachelio 模式，兼容响应体红线）
      b) 透传代理（shouldInterceptRequest 返回自建 WebResourceResponse，违反 v0.1.5 红线，不推荐首选）
   Android 侧另需 ServiceWorkerClient.shouldInterceptRequest（API 24+）拦截 SW 分发流量
   （§5.9 竞品实证；开源扩展端 webRequest 天然覆盖此项，Android 侧普遍缺失）

L2 页面脚本钩子（注入，只读不改行为）
   fetch / XMLHttpRequest.open 上报 URL
   页面上下文取回清单：注入 JS 以页面自身会话 fetch m3u8 后经 JS 桥回传内容（§5.9）
   MediaSource.addSourceBuffer / appendBuffer（MSE 流捕获或 mimeType 记录）
   Blob 构造器 Proxy（抓内存态 m3u8，~20 行）
   Worker 包装注入（cat-catch search.js）
   跨域 iframe 至少记录 src

L3 页内数据扫描
   <video>/<source> currentSrc + 播放态（已有）
   页面脚本配置深扫：播放器 JSON（mediaDefinitions / setVideo* 等）、带 quality 标签的 URL、
   base64/hex 内嵌数据（cat-catch search.js / yt-dlp 提取器正则）
   播放器指纹：flashvars / kvsplayer / html5player / xplayerSettings / stream_data
   等播放器家族识别（按家族覆盖海量同源小站，§5.9）

L4 确认、解析与会话透传
   检出即自动解析（去抖批量 inspection → master 变体/分辨率，mediago 模式）
   请求头/ Cookie / Referer 随源透传到解析与下载（mediago formatHeaders）
   本地 HTTP 代理改写（VBrowser NanoHTTPD / Cachelio LocalHlsServer）
   代际号防串页（mediago tabGenerations ≈ PureBrowser epoch，既有设计得到验证）

L5 兜底
   MSE 内存捕获重放（flowpick） / MediaRecorder 录制（cat-catch recorder.js）

支线：规则外置（legado/miru 模式）——站点适配变成可更新的数据，App 保持通用
```

## 7. 站点A／站点B 的共同特征（yt-dlp 提取器源码证据）

**站点A**（yt-dlp 对应提取器，`yt_dlp/extractor/` 下文件名含站点名，此处略）：

- 页面 HTML 内嵌 `var flashvars_<数字id> = {...};` JSON；
- 其中 `mediaDefinitions[]` 每项形如 `{videoUrl, quality}`：**多档渐进式 mp4（quality 为数字分辨率）+ hls（m3u8）+ dash（mpd）全部在列**；
- 需要年龄验证 Cookie（`age_verified=1`、`accessAgeDisclaimerPH=1` 等，共 4 个）；
- 另有 `qualityItems` 辅助结构；mpd/m3u8 提取时带请求头。

**站点B**（同上，另一提取器）：

- 页面脚本含 `html5player.setVideoUrlHigh("…mp4")` / `setVideoUrlLow(…)` / `setVideoHLS("…m3u8")`，另从 query 串解 `flv_url=`；
- 无任何特殊请求头/Cookie 要求（yt-dlp 默认 UA 即可）；
- hls 分支调用 `_extract_m3u8_formats` 展开 master 变体。

**共同点归纳**（这就是"一步一步做起，先看共同之处"的答案）：

1. **全部播放源和清晰度标签都写在页面脚本里**（L3 一条路径即可全量命中，且 quality 字段现成）；
2. **实际播放时网络层必然出现真实 m3u8/mp4/mpd 请求**（L1 可命中；桌面 UA 下站点A 很可能走 DASH——这正好落进 PureBrowser "DASH 仅标记" 的空档，是实测抓不到正文的最可能直接原因之一）；
3. **HLS 主清单天然多分辨率**（L4 解析即可枚举档位）；
4. 鉴权差异：站点B 基本无防盗链；站点A 需年龄 Cookie——**"带页面会话"是通用解**。

三条通用路径（L1/L3/L4）任一打通即可命中两站，无需逐站规则——参照产品正是这么做的。

**商业同类产品分析的直接印证**：§5.9 的产品对站点A/B 的命中路径为 ①通用网络层（m3u8 扩展名 + SW 拦截）②播放器指纹注入（`flashvars`/`html5player`，与 yt-dlp 证据互证）③DOM 特征注入（`div[data-video-id]`，站点A 系 DOM）④专用正则兜底。前三条全部通用，只有第四条是站点清单——"通用为主、清单兜底"在真实商业实现中成立。

## 9. v0.1.6 演进路线图建议

> 原则：从"共同之处"入手（§7 的三条通用路径），每步独立可验证、可回退；与 v0.1.5 红线的冲突点单列（§10）。

**Step 0 — 基线取证（先行，半天级）**
在站点A/B 详情页记录 sniffer 实际观察到的证据分布（mpd/m3u8/UNKNOWN/DOM 各多少、URL 特征），确认失败模式（DASH 通道？blob：？还是检测到但下载 403？）。产出：失败模式清单，决定后续各步的优先顺序。**不写产品代码，仅日志/调试。**

**Step 1 — 自动验证（L1/L4，最大收益/最小改动）**
学 Cachelio：候选进队列，工作线程用 `CookieManager` Cookie + 页面 Referer 探测，补 Content-Type/Content-Length/重定向后 URL；m3u8 拉正文验证并求时长。预算与限额沿用 v0.1.5 探测框架（可配额、可开关）。首步探测可借鉴竞品的 `Range: bytes=0-1` 极小请求（两个字节即得精确大小与断点支持，判容器时再拉 64KiB 前缀，§5.9）。改动面：新增探测队列服务，`ResourceSniffer` 观测入口不动。
*红线对齐：自有 HTTP 客户端行为，不读 WebView 响应体；把"用户触发"放宽为"限额自动"需要一次明确的决策（§10-D1）。*

**Step 2 — 检出即解析 + 分辨率前移（L4）**
学 mediago：去抖（~150ms）批量 inspection，检出 m3u8 即解析 master 得变体列表，资源面板直接呈现档位（复用 `HlsPlaylistParser`；建议把 codec 门禁从"拒绝"降级为"标记警告仍可选"——顺带解 TED）。epoch 防串页已有，等价验证成立。

**Step 3 — 请求头透传（L4，成本极低收益确定）**
捕获页面请求头随候选传递，解析/下载阶段原样带上。站点A 的年龄 Cookie 场景即通。备选方案：§5.9 的"页面上下文取回"（注入 JS 以页面会话 fetch 清单后经桥回传内容），可与透传并用，取决于 Step 4 注入框架的落地顺序。

**Step 4 — 页面钩子注入（L2）**
注入只读脚本：XHR/fetch 上报 URL（Cachelio 关键词表起步）+ `MediaSource.addSourceBuffer` mimeType 记录 + **Blob 构造器 Proxy**（lsd 样本，20 行）+ 跨域 iframe src 记录。全程"只读不改页面行为"以贴近红线精神（§10-D2）。同批补 `ServiceWorkerClient` 拦截（API 24+；§5.9 竞品已实证并规避 Android 11 已知问题）。

**Step 5 — 页内配置扫描（L3）**
MEDIA_SCAN 增加播放器配置深扫：通用正则（`["']?((?:https?:)?//[^"']+?\.(?:m3u8|mp4|flv))["']?` 配合邻近 quality/height 字段）、`setVideo*/flashvars` 模式、JSON 内 URL+quality 对。站点A/B、TED（`__NEXT_DATA__`）等一并受益。并引入**播放器指纹**（flashvars/kvsplayer/html5player/stream_data，§5.9）：按播放器家族而非单站匹配，是 tube 站长尾的通用钥匙。

**Step 6 — DASH 支持（L3/L4）**
先展示后下载：用 Media3 `DashManifestParser`（或移植 mpd-parser）解析 Representation 列表进资源面板；下载链路（m4s 分片+合并）视 Step 0 结论决定自研或借力 Media3 DownloadManager（注意其缓存格式与 mp4 成品导出差异）。

**远期支线**：MSE 内存捕获/录制兜底（L5）；规则外置生态（legado/miru 模式）。
