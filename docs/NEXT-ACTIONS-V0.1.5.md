## 2. 立即开始的两条实站验证线

### A：先证明通用抓取边界确实扩大

1. 补齐现有 8 个作品／4 个服务的实际上传版本、匿名可访问性与内容归属核对。当前登记是候选集，不能直接当成冻结的成功率分母。
2. 在相同设备、WebView、网络、匿名访问条件与固定操作下，先跑 **正式 v0.1.4 / code13**。保存发现、方案、成品三个阶段及失败层；样本状态／网页变化单独记录。
3. **Coffee Run 保留为旧版已能发现 MP4 的正向对照**，不预设它是旧失败→新成功。只有完整配对后才能判断成品阶段差异；更多格式选项不算成品率增益。
4. 若候选集缺少代表性旧失败，依据旧版失败分类追加获授权作品，先登记、再冻结、再测候选；保留全部原行，不根据新版成功结果倒选样本。
5. 优先修复可跨站复用的观察／分类／用户主动探测／方案缺口。每项修复配对应负例与有界夹具，真实网站负责增益证据，夹具负责可复现故障。
6. 维持原样本合同：至少 8 个不同作品／4 个独立服务，其中至少 6 个非 YouTube 作品／3 个服务；相同作品、CDN、子域、自建夹具不凑数量。分别报告发现率、方案率、可用成品率，不推断全网成功率。

**交付物：** 冻结样本清单、旧版／候选逐行配对、两项跨服务新增成品证据、通用层贡献说明、未支持场景列表。受限格式如 Theora/Vorbis 不因选样而自动扩成新承诺。

### B：定位 YouTube 403，而非继续堆探针

当前事实：Android 元数据与两轨 64 字节 Range 曾通过；完整 Sintel 传输 HTTP403，任务 FAILED，无成品。**403 根因尚未确定**，不能直接归因于 token、运行时或网络。

1. 固定同一作品、当前解析器版本、设备与访问条件；记录新解析到首个传输请求的时间、脱敏格式／长度／过期信息，以及请求语义、状态与重定向层级。
2. 比较现有固定依赖的常规传输语义与应用传输实现：范围／完整响应要求、常规参数处理、地址有效时间、请求上下文一致性。只比较公开匿名正常访问，不导入登录凭据或引入额外 token 服务。
3. 首轮诊断限定为 **最多两种单变量对照及一次完整传输尝试**；重复访问拒绝且没有新证据时停止该轮。后续轮次须由明确新假设驱动，不轮换客户端、堆头或对公网无限重试。
4. 若证明是应用实现偏差，做最小修复、针对性负例与真实完整复测；若是未支持的协议／正常访问前提／许可路线，形成 No-go 记录和范围／依赖决策提案，先交用户决定，不擅自降低验收门槛或改变 Apache-2.0 路线。
5. 成功必须走公共任务、完整双轨、封装和发布路径，并验证实际成品；元数据、地址、前缀、桌面下载均不能代替 Android 端到端通过。

**交付物：** 可复现的脱敏原因记录、最小修复及回归（如成立）、完整成品证据；否则明确阻断条件与待决策项。通用跨站线继续，不等待本线结果。

## 4. 回归、并行与证据规则

- **代码可并行，设备证据串行：** 通用观察／resolver 与 YouTube 适配器可拆成不重叠写集；公共传输、存储、封装与任务 UI 由主线统一集成。共用设备的版本安装、清数据、设置和网站配对不能并发，避免污染输入。
- 每次小修跑对应单测／设备子集；公共核心变化跑受影响集合。冻结阶段再跑全量，不能把不同源码批次的绿灯拼成一份最终通过报告。
- 已有 JVM187、核心44、API37旧链路302通过保留为现有输入的证据，不因未变部分反复花费整轮测试时间，也不把它们算作尚未执行的 API28／36、长后台或最终签名包验收。
- API37 旧链路完整回归须用带夹具／健康检查／adb reverse 的 `run_v014_regression.py --scope full` 包装器，不能直接裸跑设备脚本后把缺少夹具当产品失败。上轮完整302项耗时约22.8分钟，按阶段门安排。
- 原始失败、未测、不可比及授权／服务声明矛盾继续保留；报告在 Git ignored 的 `app/build/reports/v0.1.5/`，公开只提交脱敏摘要与可复现输入信息。
