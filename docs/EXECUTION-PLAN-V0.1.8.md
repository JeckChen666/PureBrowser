## 1. 版本定位：规则层主动提取 ＋ 格式选择器 ＋ 站点知识规模化

> **把 v0.1.7 建好的规则层从"被动观察"升级为"主动提取"，并让它能返回可选清晰度——这是"以网页视频发现和授权下载为核心"这个产品定位真正落地的关键一步。**

v0.1.7 的规则层在架构上完整、执行边界清晰，但受"无网络"约束（R4），只解决了"页面正在播放时发现媒体"这一类场景。用户已在 2026-10-04 解除该约束（§0），本版据以完成三件事：

1. **规则层网络能力（新能力主线）**：规则可声明受控抓取目标（页面／JSON API），复用既有 `RequestPolicy` 原语做目标域白名单、HTTPS-only、跨源跳转拦截与逐跳校验；网络 I/O 走 `UrlFetcher` 回调，**`RuleEngine` 保持纯函数、零 IO、JVM 可测**这一验收前提不变。
2. **格式选择器与结构化 formats**：规则不再只产出单一候选地址，而是产出带 `height/bandwidth/codecs/protocol` 的格式集合，直接填充 `MediaCandidate.variants`（`VariantSummary`），让用户真正能选 1080p／4K。移植自 yt-dlp 格式选择器（`YoutubeDL.py` 约 446 处 format 相关引用，纯逻辑、无网络依赖）。
3. **站点知识规模化**：从 v0.1.7 的 11 条规则扩到数十条，覆盖从"发现成功"到"可选清晰度保存"的完整链路。

成功口径：仍是**三率分报、以真实新增可用成品结账**。新增成品判据比 v0.1.7 更严——需为**用户选定清晰度的可打开成品**，而非仅地址发现。

## 3. 能力层次与支持合同

### A. 规则层网络能力（`media/rules/*` 扩展）

- **抓取声明**：单条规则新增 `fetch` 块（规则顶层，缺省为空数组以保持 v0.1.7 规则兼容），每项声明 `id`／`method`／`url`／`maxBytes`；`maxBytes` 必填无默认值。
- **命名组变量**：`match.path` 支持命名组与位置组，绑定为规则局部变量 `{{pageUrl}}`／`{{m1..m9}}`／`{{match.<name>}}`；模板**只允许这三种占位符**，禁止任意表达式。
- **受控传输**：`RuleFetchPolicy` 组合既有 `RequestPolicy` 原语——目标必须 https、必须命中规则 host 白名单、禁 IP 字面量与私有网段、重定向逐跳复检、跨源跳转在携带凭据时直接拒绝。请求头走枚举白名单（UA/Accept/Accept-Language/Referer），**Cookie/Authorization/Proxy-Authorization 永不在其中，由会话通道单独处理**。
- **引擎形态不变**：`fetch` 通过 `(suspend (FetchSpec) -> RuleDocument?)` 回调注入，与既有 `domSnapshot` 同构；`RuleEngine` 内不出现任何 IO 代码，`RuleEngineTest` 继续以假 fetcher 全覆盖。

### B. 格式选择器与结构化 formats

- **规则动作扩展**（枚举白名单内的能力集，原三个动作保留不动）：`jsonExtract`（内联 JSON／JSON-LD／框架数据块按受限点路径取值）、`regexExtract`（内联脚本文本或抓取文档的受限正则捕获）、`ogMeta`（OpenGraph／Twitter Card）、`parseManifest`（触发既有 HLS/DASH 解析器）。
- **格式集合**：多来源格式归一为统一 `FormatEntry`，经选择器按用户偏好（最高画质／指定高度／指定容器／按码率）产出 `VariantSummary` 列表，填充 `MediaCandidate.variants`。
- **选择器移植口径**：只移植判定逻辑与排序规则，按 §8 脱敏口径重写；不复用 yt-dlp 源码文本，不引入其依赖。

### C. 站点知识规模化

- **生成**：从上游提取器批量抽取 `_VALID_URL` 正则与解析动作线索，产出候选规则 JSON 与"需人工确认"清单；`hosts`/`path` 与命名组模板可机械生成，解析段按人工确认转写。
- **内容规范**：每条规则配正反例夹具；站点域名照实入规则数据（"支持哪些站"的正常信息）。
- **范围纪律**：本版**只做高频站**，不追求提取器总量。以"可打开成品"结账，未验证站点不入内置规则。

### D. YouTube 传输窗口门控（承接 T67，不承诺成品）

T67 三轮证据已把门控收窄为**服务端按请求形态执行的窗口策略**：短前缀闭区间与中部小跨度闭区间放行（206+FTYP），窗口外大跨度闭区间、末片、无 Range 裸 GET 一律 403；且与客户端选择、cpn、会话新鲜度、查询参数名均无关。**解析侧从未失败，失败发生在传输形态上。**

- **T88 只做规律研究**：闭区间分段的可行窗口策略（分段大小、起点推进方式、并发与顺序对门控的影响），在有界电池下产出数据。
- **不在本版承诺 YouTube 成品**。研究结论二选一：找到可行策略 → 另版整合；找不到 → YouTube 记 No-go 诚实失败，证据链闭环。
- 本项**不依赖任何 JS 运行时**：解析已成功，卡点在 Range 形态。

### E. 通用层与 YouTube

- 通用层维护不扩范围，承接 v0.1.7 C 项。
- YouTube 会话路线（B）的可行性电池（v0.1.7 T74/SESS）**尚未执行**——需用户在应用内人工登录后带 `session=true` 重跑，台账 R5 挂"待补测"；本版不重开其可行性判断，也不以"无结论"充当结论。**注意 T67 的 403 门控与会话路线是正交问题**：T74/T75 验证的是"登录会话能否解除门控"，T88 验证的是"请求形态能否绕过门控"，二者不可互相替代，也不可互相证否。

## 4. 技术选型

- 规则解释器、格式选择器、受控抓取全部纯 Kotlin；**不引入 Python、Node 或任何解释型运行时**。`RuleEngine` 零 IO、可注入假 fetcher，JVM 测试可全覆盖。
- 网络出口复用 `HttpTransport`（`fun interface`）与 `UrlFetcher` 抽象，抓取路径的头部快照沿用既有 `WATCHED_HEADERS` 白名单模式，只拷贝策略产出的头。
- **新增原生依赖：无。** 本版三条主线（规则层抓取、格式选择器、站点规模化）全部在现有 Gradle/Kotlin 构建面内完成，零新增 NDK/CMake 模块。media3 复用范围与 v0.1.6 相同。
- **规则文件仍为内置版本化 JSON**；手写容错 JSON 解析器与加载期校验风格沿用 `RuleData.kt`。
- **规则层"执行站点 JS"的能力本版不做**，载体与时点见 D11。页面上下文执行需求继续复用既有 `evaluateJavascript` 通道（`BrowserEngine`），不新增引擎。

### D5 分级：约束强度与规则来源挂钩

同一套 `fetch` 能力，两类规则来源的安全档位不同——把风险控制绑在"规则是不是我们写的"上，而不是绑死在能力上：

| 档位 | 适用 | 目标域 | 私网/IP 字面量 | 跨源跳转 | 预算 |
| --- | --- | --- | --- | --- | --- |
| **内置规则**（本版全部） | 我们编写并逐条配夹具的规则 | 命中规则 `match.hosts` | 禁 | 携带凭据时禁 | 较宽（仍受全局预算约束） |
| **用户导入规则**（D9 开启后） | 外部来源、签名有效 | 命中规则 `match.hosts` ∩ 签名信任域 | 禁 | **一律禁** | 收紧（更小 `maxBytes`、更短墙钟） |

这样 D9 的用户导入通道开启时不必重写抓取层，只需切换档位；D9 若最终 No-go（只保留内置规则），也不必为不存在的威胁收紧内置规则的能力上限。

## 8. 安全、恢复与放行

- **沿 v0.1.6 §8 与 v0.1.7 §8 全部条款**（探测/解析/下载纳入全局预算与 2 任务槽；Cookie/凭据不落任务 JSON、日志与诊断导出；观测不全如实回退、协议不支持明确说明、适配失效有界重试、内存失控/假完成/凭据泄漏/旧成功倒退阻挡发行），以及 §0 列出的六条"未被本次修订触及、继续有效"的红线。
- **预算合并账本**：规则层 `fetch` 与既有 `AutoProbeQueue` 探测共用同一每 epoch 请求预算账本（合并计数，不各自设独立上限叠加刷请求）；下载仍走全局 2 任务槽。规则触发的抓取计入"每次用户动作"预算（R4 补偿 3 的"有界"以合并口径执行）。
- **§0 中 R1–R5 的补偿约束**（凡实际采用的放开项必须逐条落位，不得缺项；其中 R4 的四条补偿如下）：
  1. **目标域**：https-only；必须命中规则 host 白名单；禁 IP 字面量、私有网段、link-local；重定向逐跳复检。
  2. **凭据**：Cookie/Authorization/Proxy-Authorization 不在规则可设头部枚举内；会话只经 `WebsiteAccessContext` 取得，域粒度由 D6 校验；不导出、不落盘、不跨注册域。
  3. **有界**：每次用户动作的请求数、总响应字节、墙钟时长三重预算；`maxBytes` 无默认值；超预算有界降级（跳过该规则，不影响通用层与既有任务）。
  4. **可见**：资源中心标注"由站点规则抓取"来源与抓取次数/字节数；确认页明示本次是否使用登录会话。
- **R1／R2／R3 的处置留痕**：三者虽经用户放开，但本版均不采用。计划与台账须写明"经放开但未采用及原因"，避免后续误读为已引入 GPL 传染组件或解释型运行时。
- **引擎纯度**：`RuleEngine` 必须保持零 IO 与零网络类型依赖，由测试守护（禁止出现 `HttpTransport`/`UrlFetcher` 等类型的字段或参数）。这是 v0.1.7"解释器纯 Kotlin（JVM 可测）"验收前提的延续。
- **来源审计（两类来源分开口径，不得混用）**：
  - **非开源竞品**：正式文档与代码注释一律不写明具体应用名称／包名，只可写"参考闭源竞品逆向分析"（沿 v0.1.7 §8 与 2026-10-04 第一条修订）。
